Intelligent Educator · architecture · 2026-10-26

High-level architecture

The Intelligent Educator, an MSc thesis tutor on a typed knowledge graph and GraphRAG: actors, subsystems, stores, external services and the main flows.

Low-level design → Evidence: code doc ours unverified

TL;DR

  1. The Intelligent Educator is a course tutor for graduate machine learning. It answers from the course books, slides and lecture transcripts, and cites book, chapter, section and page.
  2. One pure package, educator_core, does retrieval and the answer. The web app and the Stage A evaluation harness both call it, so the product runs the same rules the thesis measures.
  3. Content is built offline by thesis-pipeline: OCR, chunking and bge-m3 embeddings on Kaggle and IUST GPUs, and a typed knowledge graph (6,814 concepts, 5,866 eligible edges) extracted by Claude Opus and checked by NLI models.
  4. Online, everything runs locally in OrbStack: React + nginx, FastAPI, Postgres 17 + pgvector, Neo4j 5. The only outbound call from the app is the answer LLM on Alibaba Model Studio.
  5. Stage A compares five arms (L, R, G, H, Hc) at the same context budget, answer prompt and judges, and pins every input in one hashed manifest (I4).

01 · Context

Who uses it and what it calls

Two roles use the tutor: Student and Administrator code. An administrator also authors: placement items, prompt versions and showcase examples. The course is CS 156 (Caltech, Learning From Data) with eight ML textbooks doc. The rule is “own APIs only”: no OCR, VLM or document-processing service is called at run time; parsing happens offline doc.

02 · Subsystems

Three lanes, one answer core

The offline lane makes content; the online lane serves it; the evaluation lane measures it. The online tutor and the harness call the same educator_core.answer_once; the harness reads hashed files (FileSnapshot), the app reads Postgres and Neo4j (DbStore) code.

03 · Flows

Main flows

Four flows cover the system ours. Steps are in order; the low-level page draws flow 1 in full.

1. Ask a question

  1. Learner types a question in chat (mode text, hybrid or graph).
  2. Backend builds the turn: settings, follow-up rewrite, source policy.
  3. educator_core retrieves (R list, graph list), fuses and packs to budget B.
  4. Gate on the best cross-encoder score; else no_answer with the 3 closest passages.
  5. Answer LLM writes with [n] citations; the turn is stored; the support check runs after.

2. Build the content

  1. Corpus PDFs, slides and transcripts are planned into units (Mac).
  2. OCR, chunking and embedding run as jobs on Kaggle / IUST.
  3. Opus extracts concepts and relations; ER, NLI gate and PRE judge clean them.
  4. A KG generation and manifest freeze S_G; the seed job loads Postgres and Neo4j.

3. Placement to lessons

  1. Learner ticks covered lectures; the prior follows them.
  2. DINA CD-CAT picks items by expected entropy; free text is judged by the LLM.
  3. Mastery colours the concept map (red, yellow, green, grey).
  4. Lessons and the chat beside them use the same tutor.

4. Evaluate (Stage A)

  1. Bank items are locked away from dev and pilot.
  2. run_eval runs every arm on FileSnapshot inputs, 3 generations each.
  3. Two Alibaba judges score each answer (AND rule).
  4. gate_check, scorer and stats read the trace; I4 pins every input.
