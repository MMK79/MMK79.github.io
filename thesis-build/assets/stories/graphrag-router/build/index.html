GraphRAG, step by step

How GraphRAG chooses its path

A question can follow three kinds of link in a knowledge graph. A router reads the question and picks which kinds to follow, and in which direction.

In short

The graph arm H walks the knowledge graph from the concepts named in the question. A router decides which relation types it may follow (IS_A, USES, PREREQUISITE_OF) and in which direction. The arm Hc is the control: the same edges, the same direction and depth, but it cannot see the labels, so it follows every type. If H beats Hc, the labels helped.

Status: the thesis uses table s7-b/2 with k_graph 30 (at most 30 graph passages enter fusion), chosen on dev: a three-way tie broken by the rule fixed in advance. The page shows all three candidates. The first pilot had a placeholder router, so H and Hc were the same arm. A router alone was not enough: see the hop-0 problem.

The problem: with no router, the labels cannot matter

Hc exists to answer one question: do the relation labels carry information? H and Hc get the same edges. They differ in one rule only: H keeps an edge when its relation type is allowed by the route, and Hc keeps every edge.

In the first pilot the router was a placeholder. It allowed every relation type in both directions. Then H keeps every edge, exactly as Hc does.

EvidenceH and Hc sent identical requests on 90 of 90 generations. The H versus Hc contrast could not work until the router uses the labels. (Pilot post-mortem, section 4.)

This is not a bug in the walk. It is a missing piece: a function from the question to a route.

The idea: read the cues in the question

Questions carry cues about which link matters. "Why does X require Y" asks for what must come first. "What is X a kind of" asks for parents. "Where is X used" asks who uses X.

question→find cue (first match wins)→relation types + one direction→walk 2 hops from the seed concepts

The router is a pure function of the question text and its table. It reads no graph, no question stratum and no label of the answer. One direction applies to every relation in the route.

Edge convention"A PREREQUISITE_OF B" means A comes before B. "X IS_A Y" means X is a kind of Y. "A USES B" means A uses B. Direction in follows edges that end at the seed (its prerequisites, its children, its users). Direction out follows edges that start at it (its parents, what it uses).

The fix: a table of cues, the first match wins

A router is an ordered list of rows. Each row has a cue (a pattern in the lower-cased question), the relation types it allows and one direction. The last row has no cue and catches everything else.

Router

Taxonomy and usage cues come before the proof cue. "Why is X a special case of Y" asks about the parent of X, not about prerequisites.

    Hc: labels collapsed

      Three candidates, one fixed question set

      The experiment compares three tables on the dev set only. They differ in how many cues they know and in what they do when no cue fires.

      • s7-a/3: five typed cue rows, then a fallback that allows everything in both directions (H then equals Hc on cue-less questions).
      • s7-b/2: one proof cue, then the same open fallback.
      • s7-c/1: the cues of s7-a/3, but the fallback is typed (prerequisites, inwards), so every question walks a typed route.

      Each is tried with k_graph 10, 20 and 30 (at most 9 configurations), for H only and on the development items, by gold-evidence recall in the packed context. At k_graph 30 all three tables had equal recall (77 of 216), so the tie rule fixed in advance chose s7-b/2; R kept its fixed setting (depth 30, 10 reranked). The pilot-1 placeholder is shown in the router menu above for comparison.

      Why a router alone did not separate H and Hc

      The problem. The first registered rank rule (rule 7) sorted the graph passages by hop, then by cross-encoder score, then by id, and cut the list at k_graph. Each seed concept alone has dozens of passages. So hop-0 passages fill every slot, and the route cannot change the list: H = Hc on that item, whatever the router says.

      EvidenceIn the first pilot as run (placeholder router, k_graph 20), 29 of 30 graph lists were all hop 0; only 1 of 30 held a deeper-hop passage. Under configuration I3 (s7-b/2, k_graph 10, rule 7) with the same seed concepts, 0 of 30 lists were projected to hold one. That assumes the same linked seeds; it is a projection, not an observation. (Addendum D, D0.)

      The fix. A hop-balanced rank (hop-balanced/1) gives each hop present a quota of ⌈slots left / hops left⌉, filled by cross-encoder score; unused slots pass to later hops. Free slots are then backfilled in (hop, −CE, id) order without removing a chosen deeper passage, and the chosen set is returned in that order. It reads no relation label, so H and Hc still differ only in the eligible edges. Then the router and k_graph were tuned again, which gave s7-b/2 with k_graph 30. Graph hops and ranking shows the rule.

      What this does not fix. Under s7-b/2, 15 of 30 pilot questions take the fallback row (every relation, both directions), where H and Hc allow the same edges. A null H versus Hc result can therefore mean that the router rarely selects, not that the labels have no value. Fusion and packing can still erase deeper-hop differences, and an equal cap of k_graph is not an equal list length. (Addendum D, D1 and D10.)

      Not known yet

      Selected by a tie rule, not by a measured win. On dev, all three tables reached the same recall at k_graph 30 (77 of 216), so the choice of s7-b/2 says the dev metric did not separate them. The walks on the real items are sealed until the pilot closes, so they are not on this page.
      • Does the router help? That is the H versus Hc test. It is not answered here. Half of the pilot questions (15 of 30) take the fallback row, where the two arms allow the same edges.
