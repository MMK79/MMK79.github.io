The graph arm ranks passages by a relevance score. We needed 181,630 new scores on top of the ones we had. This page shows how we made sure that every score comes from one scorer, so no result depends on which machine did the scoring.

TL;DRthe short version

In five lines

  1. To rank passages, the system gives each (question, passage) pair a relevance score. A cross-encoder, bge-reranker-v2-m3, makes that score.
  2. The balanced rank rule needs a score for every passage at hops 0 to 2. That meant 181,630 new pairs on top of 15,443 scored ones.
  3. int8 scores can differ between CPU types. So the rule, fixed in advance: keep the old job (S1) only if every new machine reproduces 200 old scores exactly; otherwise re-score everything with one GPU job (S2).
  4. All 25 kernels, on Intel and AMD CPUs, matched 200 of 200. S1 was kept.
  5. The 197,073 merged scores cover 100 % of the pairs and were hashed before tuning, so the scores cannot change after a result is seen.
Level 0like I am five

Many graders, one grade book

Imagine a contest with thousands of essays. Each essay gets a grade, and the grades decide the winners.

Some essays already have grades. Now many new graders must grade the rest. But what if a new grader is a little stricter? Then the winners depend on who graded which essay. Nobody chose that.

So before a new grader starts, we give them 200 essays that already have grades. They must give exactly the same grades. If one grade is different, we stop all of them. Then one single grader grades every essay again, old and new.

Every new grader matched all 200. So we kept the old grades and added the new ones. Then we locked the grade book before anyone looked at the winners.

old grades→test: 200 exact→grade the rest→one grade book→lock it
Level 1student

Why one scorer must be proven, not assumed

A cross-encoder reads a question and a passage together and gives one relevance number. Ours is bge-reranker-v2-m3. We run it in int8: the model's numbers are stored as small integers, which makes it fast on a CPU.

A key is one (question, passage) pair. A kernel is one scoring job on one rented Kaggle machine. Bit-equal means the two numbers are the same in every binary digit, not only "close".

int8 arithmetic can give slightly different results on different CPU instruction sets. The machines that made the old scores did not record their instruction set. So "same model, same settings" did not guarantee the same numbers.

One real example, worked

Same model file, two kinds of CPU

On Kaggle (x86). The first kernel, the timing probe, ran on an Intel Xeon 2.20 GHz. It re-scored the 200 sample keys and matched 200 of 200 bit for bit. Then it scored 1,000 new pairs at 0.632 pairs/s.

On a Mac (ARM). A side test re-scored 50 of the same keys. The order agreed almost fully (Spearman 0.987). But 0 of 50 numbers were bit-equal, and the largest gap was 0.104.

What it means. The rank rule takes each hop's best passages by score. A score that moves can change which passages fill the slots. The Mac was never a scoring machine; the test shows why every scoring machine had to pass the check first.

The switch rule

S1 stays if and only if every S1 kernel is bit-equal on all 200 keys. One mismatch on any kernel selects S2, with no retry. The decision is recorded before any new score is merged and before any tuning; on a switch, the S1 scores are discarded, never mixed with S2. One score source per key, never mixed by arm.

Speed, cost and wall-clock time are explicitly not criteria; a slow S1 waits. This closes a quiet channel: a scorer chosen for convenience after some scores exist is still a choice that can move the ranking.

What the check proves, and what it does not

Exact equality is a defensible stop rule, not a shown feasibility. 200 equal keys support reproducibility; they do not prove equality on unseen keys. The check ran on every kernel and on both CPU types in the run, which is the strongest form the rule allows.

Cost

At about 0.5 pairs/s, 181.6k new pairs is about 100 kernel-hours; the protocol labels this an extrapolation. The run measured 0.52-0.66 pairs/s. Kaggle session and concurrency limits set the wall-clock time.

Threat recorded

44 of 50 sampled pairs reach the 512-token cap, so long exercise stems are cut. The cap is the same for every arm and frozen in both specifications; its effect on ranking is not measured.

Level 3our thesis choice

Why this matters for the result

The thesis compares a text arm with graph arms that share rank, fusion and packing code. The balanced rank rule (Addendum D) ranks inside every hop, so it needs a score for every passage at hops 0 to 2, with no cap. That is where the 181,630 new pairs came from.

What we gain

Every arm reads the same scores from the same source. The file was hashed (stage 2) before dev tuning, and the tuning code refuses any other file. So a difference between arms cannot come from which machine scored a pair, and the scores were fixed before any tuned result existed. A frozen shared-baseline comparison stays valid under either scorer.

Per-item tuning rows and retrieval traces are sealed until the pilot closes; the visible record holds aggregates and the winner. The next stage of the path, how the scores fill the graph slots, is in Graph hops and ranking.
